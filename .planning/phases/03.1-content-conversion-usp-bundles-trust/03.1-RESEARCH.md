### Pattern 1: Phase 3 Section-Level Motion Entrance (D3.1-11 contract)

**What:** Every new section wrapper uses `<m.section>` with `whileInView` fade+slide, bounded by the Tailwind `motion-reduce:` fallback. Within-section elements do NOT individually stagger (D3-11 / D3.1-11).

**When to use:** Every new section in Phase 3.1 (UspComparison, CatalogBundles wrapper, Bundles, TrustBadges).

**Example (verbatim from Phase 3 shipped code — this is the canonical pattern):**

// Source: src/sections/FlavorTeaser.tsx:117–123 [VERIFIED]
import { m } from '@/lib/motion';
import Container from '@/components/primitives/Container';
import Section from '@/components/primitives/Section';

        whileInView={{ opacity: 1, y: 0 }}

        <Container>

### Pattern 2: TrustBadge Discriminated-Union Variant

**What:** Extend the Phase 1 primitive with a `variant` prop where `visual-only` omits `evidenceUrl` from the type and `linked` keeps it required. TypeScript enforces at compile time; the runtime PROD throw only fires on the `linked` path (Phase 1 contract preserved).

**When to use:** The TrustBadge primitive extension (D3.1-08). All four Phase 3.1 trust strip badges render as `variant="visual-only"`; Phase 5 migrates each to `variant="linked"` as evidence arrives.

**Example (recommended discriminated-union signature):**
```typescript
// Source: EXTEND src/components/ui/TrustBadge.tsx
import type { ComponentType } from 'react';
import { ShieldCheck, Leaf, MapPin, Lock } from 'lucide-react';

type TrustBadgeLabel =
  | 'FSSAI Licensed'
  | 'Plant-based ingredients'
  | 'Made in India'
  | 'Secure Checkout';

// Discriminated union — TS enforces: variant='linked' REQUIRES evidenceUrl;
// variant='visual-only' DOES NOT allow evidenceUrl.
export type TrustBadgeProps =
  | {
      variant?: 'linked';          // default (preserves Phase 1 contract)
      label: TrustBadgeLabel;
      value?: string;
      evidenceUrl: string;         // REQUIRED
      icon?: 'leaf' | 'shield' | 'check' | 'star';
    }
  | {
      variant: 'visual-only';      // explicit opt-in to Phase 3.1 variant
      label: TrustBadgeLabel;
      value?: string;
      icon?: 'leaf' | 'shield' | 'check' | 'star';
      // NOTE: no evidenceUrl in this arm → attempting to pass it is a TS error
    };

export function TrustBadge(props: TrustBadgeProps) {
  if (props.variant === 'visual-only') {
    // visual-only — static icon + label; no <a>, no PROD throw, no dev warning
    const Icon = iconFor(props.icon ?? defaultIconFor(props.label));
    return (
      <span
        aria-label={props.label}
        className="inline-flex items-center gap-2 rounded-full border border-[color:var(--color-border)] bg-[color:var(--color-surface)] px-3 py-2 text-sm text-[color:var(--color-fg)]"
      >
        <Icon size={16} strokeWidth={2} aria-hidden="true" />
        <span>{props.label}</span>
        {props.value ? (
          <span className="text-[color:var(--color-fg-muted)]">· {props.value}</span>
        ) : null}
      </span>
    );
  }
  // variant === 'linked' (default) — Phase 1 behavior UNCHANGED, including
  // the import.meta.env.PROD throw and dev-only `data-pending-fssai` warning
  // when evidenceUrl is empty. Preserves TRUST-01 production refusal contract.
  // ... existing Phase 1 render path, byte-identical ...
}

function defaultIconFor(label: TrustBadgeLabel) {
  switch (label) {
    case 'FSSAI Licensed':          return 'shield';
    case 'Plant-based ingredients': return 'leaf';
    case 'Made in India':           return 'check';   // or Claude's discretion to swap MapPin/Flag
    case 'Secure Checkout':         return 'check';   // Lock is the actual icon — map here
  }
}
```

**Why discriminated union, not optional prop:**
- An optional `evidenceUrl?: string` + optional `variant?` would let `variant="visual-only"` AND `evidenceUrl` coexist — ambiguous and allows the Phase 1 PROD throw to fire on a `visual-only` badge if a future author forgets to pass `evidenceUrl` and defaults `variant` to `linked`. Discriminated union makes `visual-only` + `evidenceUrl` a compile-time error (correctly surfaces author intent) [CITED: TypeScript handbook — Discriminated Unions].
- The default `variant?` in the `linked` arm preserves the Phase 1 contract: any current callsite that passes `{ label, evidenceUrl }` without `variant` still compiles and renders through the Phase 1 linked path.

### Pattern 3: Centralized `getCta()` with Dotted-String Bundle Slots

**What:** Extend `src/config/cta.ts` to populate the `bundles.{trial|fitness|bulk}` slots with WhatsApp URLs and extend `getCta()` to accept the three new slot keys. Preserve the Phase 1 single-site invariant (CI grep allowlists ONLY `src/config/cta.ts` for `wa.me`).

```typescript
// Source: EXTEND src/config/cta.ts
// Base message pattern established in Phase 1 D-08:
//   "Hi! Add me to the CAPSHOT waitlist." → wa.me text `Hi%21%20Add%20me%20to%20the%20CAPSHOT%20waitlist.`
// Phase 3.1 bundle CTAs ride-along the SAME pre-fill message but add a
// `?tier=` query so the WhatsApp inbox can bucket inbound leads by tier.
// NOTE: wa.me URL spec permits query params alongside `?text=` — WhatsApp
// strips them from the delivered message but they persist in the deep-link
// so analytics / inbox-side filters CAN read them (via UTM-style ingestion
// or a BSP integration later). For Phase 3.1 the attribution channel is
// manual (the brand reads the tier param from the referring link in their
// WhatsApp Business desktop app).

export type CtaSlot =
  | 'primary'
  | 'secondary'
  | 'nav'
  | 'bundles.trial'
  | 'bundles.fitness'
  | 'bundles.bulk';

export const ctaConfig = {
  primary:   { /* ... unchanged ... */ },
  secondary: { /* ... unchanged ... */ },
  nav:       { /* ... unchanged ... */ },
  bundles: {
    trial:   'https://wa.me/919203975762?text=Hi%21%20Add%20me%20to%20the%20CAPSHOT%20waitlist.&tier=trial',
    fitness: 'https://wa.me/919203975762?text=Hi%21%20Add%20me%20to%20the%20CAPSHOT%20waitlist.&tier=fitness',
    bulk:    'https://wa.me/919203975762?text=Hi%21%20Add%20me%20to%20the%20CAPSHOT%20waitlist.&tier=bulk',
  },
} satisfies {
  primary:   CtaDestination;
  secondary: CtaDestination;
  nav:       CtaDestination;
  bundles:   Record<'trial' | 'fitness' | 'bulk', string>;
};

export function getCta(slot: CtaSlot): CtaDestination {
  if (slot.startsWith('bundles.')) {
    const key = slot.split('.')[1] as 'trial' | 'fitness' | 'bulk';
    return {
      label: 'Join waitlist for early access',     // D3.1-06 phase-invariant
      href: ctaConfig.bundles[key],
      kind: 'whatsapp' as const,
      ariaLabel: `Join the CAPSHOT ${key} pack waitlist on WhatsApp`,
      trackingId: `cta_bundle_${key}_whatsapp`,
    };
  }
  // Phase 1 slots (primary | secondary | nav) → direct lookup, unchanged shape
  return ctaConfig[slot as 'primary' | 'secondary' | 'nav'];
}
```

**Why dotted-string over function overloads:**
- Overloads would require every call site (and PrimaryCTA's `slot` prop type) to know ALL overload arms — adding a Phase 6 slot would widen every signature. [CITED: TypeScript handbook — Overload Signatures and Implementation]
- Dotted-string keys keep the `getCta(slot: CtaSlot)` surface single-signature; adding `'bundles.*'` is a union-type addition, no overload reshuffling.
- Preserves the Phase 1 convention `getCta('primary' | 'secondary' | 'nav')` — new values ADD to the union without widening the function signature.

**wa.me URL encoding (CRITICAL — Phase 1 D-09):**
- `!` → `%21` (verified in `src/config/cta.ts`:41 and :54 — `Hi%21%20Add%20me%20...`)
- The `?tier=trial|fitness|bulk` query is appended with `&tier=...` (NOT `?tier=...`) because the URL already has a `?text=...` query. If the planner reorders, the first query param must use `?` and subsequent use `&`.
- Spaces → `%20` (not `+` — `wa.me` honors both but `%20` is the project convention per Phase 1).

## Common Pitfalls

### Pitfall 1: Breaking the CI grep gate with the "Bulk Energy Pack" bundle name
**What goes wrong:** A dev writes `"Bulk Energy Pack"` directly into a `src/sections/Bundles.tsx` component template. The CI grep gate [VERIFIED: `scripts/ci-grep-forbidden-strings.mjs`:61] uses `/energy\s+drink/i` — "energy pack" is permitted, but "energy drink" is NOT. The regex is case-insensitive and requires whitespace between the two words.
**Why it happens:** The gate was designed to catch "energy drink" positioning (a FSSAI compliance issue); it does NOT look for "energy" alone. All three bundle names + descriptions below are safe:
  - `handle: 'bulk-energy-pack'` ✅ (energy-pack, not energy drink)
  - `title: 'Bulk Energy Pack'` ✅ (energy pack, not energy drink)
  - `audience: 'For heavy gym-goers and athletes'` ✅
  - `description: '30 caps for serious hydration habits.'` ✅
**How to avoid:** Run `npm run grep:ci` locally before committing any Phase 3.1 section. The CI will run it automatically.
**Warning signs:** `✖ ... CI grep violation found.` in CI output. The script prints `file:line` and the offending substring.

### Pitfall 2: Forgetting the `motion-reduce:` Tailwind fallback on new `<m.section>` elements
**What goes wrong:** A new section's `<m.section>` has `initial={{ opacity: 0, y: 32 }}` + `whileInView`. For a user with `prefers-reduced-motion: reduce`, Motion emits the inline `style="opacity:0;transform:translateY(32px)"` and does NOT auto-collapse to final state — the entrance IS suppressed by Motion internally, BUT the inline style attribute still carries initial-state values until the IntersectionObserver fires. On a slow mid-tier mobile the user may see the section at opacity:0 for up to a frame.
**Why it happens:** Phase 3 established the pattern via a Tailwind utility — not Motion's own reduced-motion detection — because the Tailwind utility is a pure CSS override (no re-render) that forces final-state immediately regardless of Motion's internal state. [VERIFIED: `src/lib/useReducedMotion.ts`:36–43 comment explaining the strategy choice.]
**How to avoid:** EVERY `<m.section>` in Phase 3.1 MUST carry `className="motion-reduce:!transform-none motion-reduce:!opacity-100"`. Mirror the FlavorTeaser `<m.section>` class list exactly.
**Warning signs:** FT-P3-2-style Playwright assertion (`expect(wrapperOpacity).toBe('1')` under `reducedMotion: 'reduce'`) fails on the new section's wrapper. The new specs MUST include this assertion per D3.1-11.

### Pitfall 3: Loosening the TrustBadge `label` strict union
**What goes wrong:** A dev adds `"FSSAI Approved"` or `"Vegan & Non-GMO"` as a new label (perhaps misreading the Phase 5 blueprint). TypeScript errors; dev loosens the union to `string`. CI passes; production ships with regulator-incorrect phrasing.
**Why it happens:** The Phase 1 compile-time contract [VERIFIED: `src/components/ui/TrustBadge.tsx`:20–24] is the ONLY guard against regulator-incorrect labels. FSSAI's 2026 nomenclature is "Licensed" (not "Approved") and the FSSAI vegan logo is still client-pending (D3.1 Deferred Ideas).
**How to avoid:** DO NOT widen the `TrustBadgeLabel` type. The four locked strings in D3.1-07a (`'FSSAI Licensed'`, `'Plant-based ingredients'`, `'Made in India'`, `'Secure Checkout'`) are the complete set for Phase 3.1 AND Phase 5. If a new label is EVER needed, it comes with a dedicated regulatory review.
**Warning signs:** A PR that adds a 5th string literal to the `label` union. Fail code review.

### Pitfall 4: Appending `?tier=` as a second `?` in the WhatsApp URL
**What goes wrong:** A dev writes `https://wa.me/919203975762?text=...?tier=trial` (two `?` separators). Browsers treat the second `?` as part of the first query value — the URL becomes `?text=Hi%21%20Add%20me%20to%20the%20CAPSHOT%20waitlist.?tier=trial` — the `tier` attribute is NOT a separable query param. WhatsApp inbox-side attribution reads "trial" as part of the message body.
**Why it happens:** The author remembered "query = ?param=value" but didn't notice the URL already has a `?text=` query.
**How to avoid:** Use `&tier=...` for the second query param. Pattern (VERIFIED above in Pattern 3):
```
https://wa.me/919203975762?text=Hi%21%20Add%20me%20to%20the%20CAPSHOT%20waitlist.&tier=trial
```
The CTA e2e spec should assert that the href contains BOTH `?text=` AND `&tier=trial`.
**Warning signs:** The CTA e2e `expect(href).toContain('&tier=trial')` fails but `expect(href).toContain('tier=trial')` passes — likely a `?tier` instead of `&tier`.

### Pitfall 5: Breaking the FlavorTeaser byte-identical relocation contract
**What goes wrong:** A dev relocating `<FlavorTeaser />` into `<CatalogBundles>` wrapper also "optimizes" the FlavorTeaser's wrapping Section/Container stack because the new parent (CatalogBundles) already provides a Section. Result: FlavorTeaser's `Section` className changes, `pt-*` is removed, and FT5 (scroll-snap `x mandatory`) or FT-P3-1 (motion-wrapper class check) break.
**Why it happens:** D3.1-05a says parent-only change. But the "right" minimal diff is NON-OBVIOUS when CatalogBundles already wraps a `<Section>` — a cleanup-minded dev will double-nest and then undo.
**How to avoid:** Keep CatalogBundles as a semantic `<section>` or a plain `<div>` (NOT the `<Section>` primitive) so FlavorTeaser's own `<Section>` wrapper stays. The CatalogBundles wrapper owns only the H2 heading, the eyebrow, the connecting narrative between Step 1 and Step 2, and the Bundles lane. **Diff must be:**
```typescript
// src/pages/HomePage.tsx — BEFORE
<FlavorTeaser />
// src/pages/HomePage.tsx — AFTER
<CatalogBundles />
// where CatalogBundles.tsx renders:
<section aria-labelledby="catalog-heading" className="...">
  <Container><h2 id="catalog-heading">Pick your CAPSHOT</h2> ...</Container>
  <FlavorTeaser />          {/* ← byte-identical child; its own Section stays */}
  <Container>...narrative...</Container>
  <Bundles />
</section>
```
**Warning signs:** `npm run test:e2e tests/e2e/flavor-teaser.spec.ts` fails on FT1 (region visibility), FT5 (scroll-snap), FT-P3-1 (motion wrapper), or FT-P3-2 (reduced-motion opacity:1). ALL six FT1-FT6 + two FT-P3-* MUST pass unchanged.

### Pitfall 6: Rendering the whole bundle card as a single `<a>` wrapper
**What goes wrong:** A dev wraps each bundle card in `<a href={getCta('bundles.trial').href}>` for maximum tap-area. Screen readers now announce the full card content (name + price + includes + audience + CTA label) as a single link name — ~40 words. Also, the "Best Value / Most Popular" ribbon on the Fitness card becomes part of the link's accessible name.
**Why it happens:** Marketing convention — "the whole card is clickable" is UX folklore.
**How to avoid:** Follow D3.1 Claude's Discretion rule: "the whole card is NOT a single `<a>` wrapper (the CTA is the primary tap target); card itself has visible focus state when CTA is focused." The `BundleCard` is a `<div role="group">` or `<article>`; the CTA inside is the only `<a>`. Mobile tap-area is enforced by the CTA's 48–56px height.
**Warning signs:** axe-core / Lighthouse Accessibility audit flags "link text too long" or "redundant link content." Also, the Playwright `getByRole('link', { name: 'Trial Pack' })` matches 2+ links instead of 1 (card wrapper + CTA inside).
