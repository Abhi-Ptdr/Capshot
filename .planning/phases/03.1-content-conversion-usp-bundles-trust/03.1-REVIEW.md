## Summary

Phase 3.1 ships three new homepage sections (UspComparison, CatalogBundles with embedded Bundles tri-card, TrustBadges), a `BundleCountBadge` SVG primitive, a `visual-only` arm on `TrustBadge`, and a dotted-string bundle slot extension to `getCta`. ## Critical Issues

### CR-01: `getCta` silently returns `undefined` for unknown dotted slots, violating its signature

**File:** `src/config/cta.ts:95-107`
**Issue:** The function is declared `getCta(slot: CtaSlot): CtaDestination` — i.e., it is typed to NEVER return `undefined`. But the implementation branches on `slot.startsWith('bundles.')` and, in the non-bundles branch, performs:

```ts
return ctaConfig[slot as 'primary' | 'secondary' | 'nav'];
```

This is a type assertion that erases the discriminated-union safety. If any caller — now or in a future phase — passes a dotted slot the compiler widens to `string` (e.g., `getCta(someDynamicSlot)` where `someDynamicSlot: string`), the function will:

1. Pass `startsWith('bundles.')` for a `bundles.foo` string that isn't `trial|fitness|bulk`, then call `ctaConfig.bundles[undefined as never]` and build a `CtaDestination` with `href: undefined` and `trackingId: "cta_bundle_undefined_whatsapp"`.
2. For any OTHER unknown dotted or non-dotted slot, return `ctaConfig[slot]` which is `undefined`. Downstream `cta.href`, `cta.label`, `cta.ariaLabel` crash with `TypeError: Cannot read properties of undefined`.

The only reason this isn't exploding in production today is that every call site uses a literal `CtaSlot` value. One `string` upgrade (e.g., reading a slot from CMS data, Shopify metafield, URL hash in Phase 6) breaks the invariant silently.

Also note: `startsWith('bundles.')` is a prefix check — a hypothetical future `CtaSlot` value `'bundles.subscription'` passes the prefix test but `ctaConfig.bundles[key]` returns `undefined`, and the function returns `{ href: undefined, label: 'Join waitlist for early access', ... }` — rendered CTA has `href="undefined"` (literal string) in the DOM.

**Fix:**
```ts
export function getCta(slot: CtaSlot): CtaDestination {
  if (slot === 'bundles.trial' || slot === 'bundles.fitness' || slot === 'bundles.bulk') {
    const key = slot.slice('bundles.'.length) as 'trial' | 'fitness' | 'bulk';
    return {
      label: 'Join waitlist for early access',
      href: ctaConfig.bundles[key],
      kind: 'whatsapp',
      ariaLabel: `Join the CAPSHOT ${key} pack waitlist on WhatsApp`,
      trackingId: `cta_bundle_${key}_whatsapp`,
    };
  }
  // Exhaustive narrowing on the remaining union members:
  const base = ctaConfig[slot];
  if (!base) {
    throw new Error(`getCta: unknown slot "${slot}"`);
  }
  return base;
}
```
Explicit equality checks against each literal `bundles.*` slot keep TypeScript narrowing honest, and the throw turns a silent `undefined` into a visible failure during dev.

## Warnings

### WR-01: `&tier=` query param is dead code for its stated purpose

**File:** `src/config/cta.ts:30-33, 82-86`
**Issue:** The comment claims:

> `&tier=` attribution query so the WhatsApp Business inbox can bucket inbound leads by bundle tier.

This is factually incorrect. The `wa.me` link spec propagates only the `text` parameter into the WhatsApp conversation; every other query param is dropped on the client side before the message is composed. The recipient (WhatsApp Business inbox) never sees `tier=trial|fitness|bulk`. Attribution works only via the `data-cta={cta.trackingId}` click-side instrumentation.

Impact: Operators reading the inbox will NOT be able to bucket leads by tier as the comment promises. The query param is harmless (not forwarded, no security impact) but is misleading documentation and dead-weight on the URL.

**Fix:** Either (a) encode tier into the `text` body so it's visible in the inbound message:
```ts
trial: 'https://wa.me/919203975762?text=Hi%21%20Add%20me%20to%20the%20CAPSHOT%20Trial%20pack%20waitlist.',
```
or (b) delete the `&tier=` and update the comment to say "tier attribution happens via `data-cta` tracking only."

Note: the e2e spec `catalog-bundles.spec.ts:72-90` grep-locks `&tier=…` so changing the URL requires updating that spec in lockstep.

### WR-02: `TrustBadge` discriminated union is leaky via the default `variant` arm

**File:** `src/components/ui/TrustBadge.tsx:43-57`
**Issue:** The LINKED arm declares `variant?: 'linked'` — i.e., `variant` is optional on the linked arm. This defeats discriminated-union exhaustiveness in two ways:

1. `<TrustBadge label="FSSAI Licensed" evidenceUrl="x" />` with no `variant` matches BOTH arms (visual-only requires `variant: 'visual-only'`, so it is excluded; the linked arm matches because `variant` is optional). This works today but a future third `variant` arm would need to be added very carefully to avoid overlap.
2. `<TrustBadge variant="linked" label="FSSAI Licensed" />` without `evidenceUrl` is a compile error on the linked arm (good) — BUT if a caller writes `<TrustBadge label="FSSAI Licensed" />` with no variant, TypeScript picks the linked arm, which then flags `evidenceUrl` as missing. Confusing error.

More importantly, the discriminator (`variant`) is OPTIONAL on one arm and REQUIRED on the other — this is a well-known TS gotcha and makes `switch (props.variant)` exhaustiveness non-trivial.

**Fix:** Make `variant` required on both arms:
```ts
export type TrustBadgeProps =
  | { variant: 'linked'; label: TrustBadgeLabel; value?: string; evidenceUrl: string; icon?: 'leaf' | 'shield' | 'check' | 'star'; }
  | { variant: 'visual-only'; label: TrustBadgeLabel; value?: string; icon?: 'leaf' | 'shield' | 'check' | 'star'; };
```
If the "default is linked" ergonomic is desired, keep it as a wrapper component (`<LinkedTrustBadge>`) rather than making the discriminator optional.

### WR-03: `getCta('secondary')` has `kind: 'external'` but `href: '/flavors'` (internal route)

**File:** `src/config/cta.ts:68-73`
**Issue:** The `secondary` CTA points at the internal React Router route `/flavors` but is tagged `kind: 'external'`. This conflates "not a WhatsApp link" with "external URL." Downstream code that branches on `kind === 'external'` to open a new tab (`target="_blank"`) would incorrectly open the internal `/flavors` route in a new tab, breaking SPA navigation.

The `CtaKind` union is `'whatsapp' | 'shopify' | 'external'`. There is no `'internal'` or `'route'` kind. Either:
- Add a `'route'` kind for client-side links, or
- Fix this entry to use a distinct kind.

Even though no caller currently branches on `kind` (verified via grep), the type is public API and the mislabeling will cause subtle bugs when the first consumer appears.

**Fix:**
```ts
export type CtaKind = 'whatsapp' | 'shopify' | 'external' | 'route';

secondary: {
  label: 'SEE FLAVORS',
  href: '/flavors',
  kind: 'route' as const,
  trackingId: 'cta_secondary_flavors',
},
```

### WR-04: Three sections pass `pt-8 sm:pt-12 md:pt-16` on top of `<Section>`'s baked-in `py-8 sm:py-12 md:py-16` — relies on tailwind-merge semantics for a visual contract

**File:** `src/sections/Bundles.tsx:63`, `src/sections/UspComparison.tsx:69`, `src/sections/TrustBadges.tsx:40`
**Issue:** `<Section>` already emits `py-8 sm:py-12 md:py-16` via `cn()` (`src/components/primitives/Section.tsx:30`). Each new section then passes `className="pt-8 sm:pt-12 md:pt-16"`, which tailwind-merge resolves by letting `pt-*` win over `py-*`'s top side, leaving `py-*`'s bottom. Net result today is `pt-8 pb-8` at the SM breakpoint — which equals the baseline `py-8`. The code works ONLY because the override values happen to equal the defaults.

Problems:
1. The intent is unclear — a reader can't tell whether the authors meant to double the top padding or match it. The comment doesn't mention it.
2. If a future tailwind-merge upgrade changes resolution order, or if a dev edits `Section`'s defaults to different values, these three sections' spacing silently drifts.
3. FlavorTeaser (`src/sections/FlavorTeaser.tsx:116`) does the SAME thing — pattern propagated without comment.

**Fix:** Either (a) remove the redundant `pt-*` override entirely (recommended — the default `py-*` already does the right thing); or (b) add a `paddingTop?: boolean` prop to `<Section>` for intentional override; or (c) at minimum, add an inline comment explaining why the override is needed.

### WR-05: TB5 2x2-wrap test is layout-dependent and brittle on `justify-center` + `flex-wrap`

**File:** `tests/e2e/trust-badges.spec.ts:90-106`
**Issue:** TB5 asserts the trust-badge strip wraps to 2x2 on 360×640 by comparing `items.nth(2).y > items.nth(0).y + items.nth(0).height * 0.5`. This is a geometry assertion that depends on:
- Badge content widths (icon + text labels like "Plant-based ingredients" is the longest at ~160px rendered)
- Font metrics (if `--font-display` fallback renders at a slightly different size)
- `gap-3 sm:gap-4` resolving to `12px` at 360px
- The browser's actual flex wrap behavior

If the badges happen to compress or if a future label is shortened, they might fit in one row and this test fails without any actual bug being present. More importantly, the test does NOT assert 2x2 — it only asserts "3rd item is below 1st." A degenerate 1+3 or 1+1+1+1 layout also passes.

**Fix:** Assert the stricter 2x2 contract explicitly:
```ts
const positions = await Promise.all([0, 1, 2, 3].map(i => items.nth(i).boundingBox()));
expect(positions[0]!.y).toBe(positions[1]!.y);  // row 1
expect(positions[2]!.y).toBe(positions[3]!.y);  // row 2
expect(positions[2]!.y).toBeGreaterThan(positions[0]!.y);  // row 2 below row 1
```
Plus pin the viewport device to a known-metric emulation and consider explicitly setting font-size via CSS override in the test fixture to decouple from font loading.

### WR-06: CB6 motion-wrapper assertion is too permissive (`>= 2` across 5 wrappers)

**File:** `tests/e2e/catalog-bundles.spec.ts:103-114`
**Issue:** CB6 counts all `<section class="motion-reduce:\!transform-none">` on the page and asserts `>= 2`. By the time the page reaches CatalogBundles, there are motion wrappers in UspComparison (1), CatalogBundles heading band (1), FlavorTeaser (1), and Bundles (1) — i.e., 4+. The `>= 2` floor is trivially satisfied even if either the CatalogBundles heading wrapper OR the Bundles tri-card wrapper is accidentally deleted — the regression it claims to guard will slip through.

**Fix:** Scope the selector to the catalog section's descendants and assert exact count:
```ts
const motionWrappers = page.locator(
  'section[aria-labelledby="catalog-heading"] section.motion-reduce\\:\\!transform-none'
);
await expect(motionWrappers).toHaveCount(3);  // heading band + Bundles tri-card + FlavorTeaser
```

Same concern applies to TB6 (`trust-badges.spec.ts:108-122`) with its `>= 1` floor.

### WR-07: Four levels of nested `<section>` under one `<main>` — a11y landmark soup

**File:** `src/sections/CatalogBundles.tsx:37-67`, `src/sections/Bundles.tsx:62-162`, `src/sections/FlavorTeaser.tsx:116-197`
**Issue:** The DOM for CatalogBundles produces this landmark nesting:
```
<section aria-labelledby="catalog-heading">
  <section class="motion-reduce...">       ← heading band motion wrapper
    <!-- h2 + intro -->
  </section>
  <section>                                 ← FlavorTeaser's <Section>
    <section class="motion-reduce...">     ← FlavorTeaser's <m.section>
      <!-- flavor scroller -->
    </section>
  </section>
  <section>                                 ← Bundles's <Section>
    <section class="motion-reduce...">     ← Bundles's <m.section>
      <!-- bundle cards -->
    </section>
  </section>
</section>
```

That's 7 `<section>` elements with mostly no `aria-label` / `aria-labelledby`, which screen readers announce as "section, section, section, section" when navigating landmarks. Only `catalog-heading` is labeled.

The motion wrappers use `<m.section>` purely for animation — these should be `<m.div>` instead, since they carry no semantic grouping. Likewise, `<Section>`'s default `as="section"` (`src/components/primitives/Section.tsx:21`) means every section already starts as a landmark; wrapping another `<section>` inside a `<Section>` creates duplicate landmarks for the same content region.

**Fix:**
1. Change `<m.section>` → `<m.div>` across all five Phase 3.1 motion wrappers (`UspComparison.tsx:70`, `CatalogBundles.tsx:40`, `Bundles.tsx:64`, `TrustBadges.tsx:41`, and the existing `FlavorTeaser.tsx:117`). The animation contract is unaffected; the landmark pollution goes away.
2. In `CatalogBundles.tsx`, override the inner `<Section>`s' `as="div"` prop so the inner children don't double up as sections. (This also preserves the outer `<section aria-labelledby="catalog-heading">` as the sole semantic landmark for the two-step narrative.)

Lighthouse Accessibility and screen-reader review will flag this.

## Info

### IN-01: Doc/code mismatch — Bundles comment claims `<article>` but code renders `<li>`

**File:** `src/sections/Bundles.tsx:34-36`
**Issue:** The comment says:
> The whole card is NOT a single `<a>` — RESEARCH §Pitfall 6: the card is an `<article>` (role=group implicit) and the only `<a>` is the CTA at the bottom.

But the actual code (line 88) renders `<li data-bundle={bundle.tier} …>`, not `<article>`. An `<li>` has no implicit `role=group`. If the authors intended `<article>` semantics, they should change the element; if `<li>` is correct, update the comment to not mislead the next reader.

**Fix:** Either change `<li>` to `<li role="group">` + `<article>` inside, or update the comment to match reality.

### IN-02: `Bundle.handle` and `Bundle.tier` encode the same information twice

**File:** `src/data/bundles.ts:26-27`, `src/data/types.ts:21`
**Issue:** Each bundle carries both `handle: BundleTier` (`'trial-pack' | 'fitness-pack' | 'bulk-energy-pack'`) and `tier: 'trial' | 'fitness' | 'bulk'`. The tier is just the handle with the `-pack` / `-energy-pack` suffix stripped. If a future bundle is added (e.g., `'subscription-pack'`), the tier must be updated separately — easy to desynchronize.

**Fix:** Derive `tier` from `handle` at the call site:
```ts
const tier = bundle.handle.replace(/-pack$/, '').replace(/-energy$/, '') as 'trial' | 'fitness' | 'bulk';
```
or (cleaner) make `tier` the canonical field and have `handle` be derived. The handle is a Phase 6 Shopify concern; the tier is a Phase 3.1 UI concern.

### IN-03: `BundleCountBadge` `padStart(2, '0')` is a no-op for `30`

**File:** `src/components/ui/BundleCountBadge.tsx:33`
**Issue:** `String(30).padStart(2, '0')` returns `"30"` — padStart only pads when length is less than target. For `count: 5` it correctly produces `"05"`. The code is correct but the comment claims "count padded to 2 digits" universally. If `count` is ever widened past 2 digits (99+), the comment is still correct but the "zero-padding" aesthetic becomes irrelevant.

**Fix:** Optional — add inline comment: `// '05' | '15' | '30' (padStart no-op for 15/30, zero-pads 5)`.

### IN-04: `TrustBadge` icon map omits one of the two icon sources — `icon?: 'leaf' | 'shield' | 'check' | 'star'` is accepted but ignored

**File:** `src/components/ui/TrustBadge.tsx:49, 55, 76-134`
**Issue:** Both arms of `TrustBadgeProps` accept an optional `icon?: 'leaf' | 'shield' | 'check' | 'star'` prop, but the component never reads `props.icon` — it always uses `iconFor(label)` which does a `switch (label)`. Dead-prop code. Any caller passing `<TrustBadge label="FSSAI Licensed" icon="star" />` is silently ignored.

Also, the `icon` union includes `'check'` and `'star'` which are not in `iconFor()`'s switch at all.

**Fix:** Remove the `icon?: …` prop from both arms (preferred, since label fully determines icon by D3.1-07a), or wire it through: `const Icon = props.icon ? iconMap[props.icon] : iconFor(props.label);`.

### IN-05: `trustbadge.spec.tsx` test "rejects a non-union label at compile time" is a no-op at runtime

**File:** `tests/unit/trustbadge.spec.tsx:44-55`, `tests/unit/trustbadge.spec.tsx:85-92`
**Issue:** The test renders nothing and asserts `expect(typeof forbidden).toBe('function')` — this passes trivially (arrow functions are always typeof 'function'). The intent is to catch a TS compile error via `@ts-expect-error`, which is a tsc-time check, not vitest-time. The test does nothing useful at runtime; it only serves as a documentation anchor.

This is fine as a convention IF the project runs `tsc --noEmit` in CI (the comment claims it does). Otherwise, deleting the type assertion in `TrustBadgeProps` would silently remove the `@ts-expect-error` requirement without any test failure.

**Fix:** Document in a comment at the top of the file that these tests rely on `tsc --noEmit` for enforcement; otherwise the "test" is theater. Optionally, replace with a real runtime test such as rendering a stub component that passes an untyped prop via `as any` and verifying the component's own runtime label validation (if added).
