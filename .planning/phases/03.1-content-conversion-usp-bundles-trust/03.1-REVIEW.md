### WR-01: Dark-mode WCAG AA contrast fail on new Step 1 / Step 2 marker label text

**File:** `src/sections/CatalogBundles.tsx:102-104`, `src/sections/CatalogBundles.tsx:125-127`
**Issue:** Both newly-added step markers render their label text with:

```tsx
<span className="text-sm font-bold tracking-wider text-[color:var(--color-brand-rose)] uppercase">
  Step 1 — Pick your flavor
</span>
```

The label color is `--color-brand-rose` (`#9E7676`). In **dark mode**
(`.dark` scope, `src/index.css:63`), `--color-bg` swaps to `#594545`
(brand-deep). The label text therefore paints brand-rose on brand-deep.

Measured contrast ratio for #9E7676 on #594545 ≈ **2.28:1**.

WCAG AA thresholds:
- Normal text (<18px / <14px bold): 4.5:1
- Large text (≥18px or ≥14px bold): 3:1

`text-sm font-bold` = 14px bold → qualifies as "large" → requires 3:1 →
**FAILS at 2.28:1 in dark mode**.

Why this is a new regression and not pre-existing: before this gap-closure
wave, the only brand-rose-on-dark-bg occurrence in this section was the
heading-band eyebrow "Flavor + pack" (`CatalogBundles.tsx:69`). The two new
step-marker labels add two more occurrences — the dark-mode contrast
problem is now the dominant visual pattern of Step 1 and Step 2, not an
incidental eyebrow. Phase 1 contrast fix (`src/index.css:58`) already
hardened `--color-fg-muted` to `rgba(255,248,234,0.70)` for AA in dark
mode; this gap-closure wave re-introduces the pattern the Phase 1 fix was
written to prevent.

The circled badge pill itself passes: `#9E7676` background on `#FFF8EA`
foreground ≈ 3.91:1, >3:1 for large text. Only the adjacent step label
fails.

The project's CLAUDE.md Constraints block explicitly locks the design to
"light/dark swap with WCAG AA" — this finding is a direct violation of
that constraint.

**Fix (any of three):**

1. (preferred) Swap the label to a foreground token that respects the dark
   swap:
   ```tsx
   <span className="text-sm font-bold tracking-wider text-[color:var(--color-fg)] uppercase">
   ```
   `--color-fg` is `#594545` in light and `#FFF8EA` in dark → both AA.
   The brand-rose color accent is already carried visually by the pill
   next to the label, so moving the text to `--color-fg` loses no brand
   identity.
2. Introduce a `.dark` variant override:
   ```tsx
   className="... text-[color:var(--color-brand-rose)] dark:text-[color:var(--color-brand-cream)]"
   ```
3. Keep brand-rose but render the labels only in the badge pill (drop the
   adjacent "Step 1 — ..." span and move its text inside the pill with the
   pill's existing brand-cream text color). Visual redesign — product
   decision.

Options 1 and 2 are zero-visual-change in light mode. Option 1 is a
one-token swap; option 2 is a one-class addition.

Note: pre-existing brand-rose eyebrow and UspComparison right-column cells
have the same light/dark contrast behavior and are intentionally out of
scope for this iteration (not touched by the gap-closure wave).

### WR-02: UspComparison asterisk footnote has no programmatic association with the "₹24-₹30 per cap*" cell

**File:** `src/sections/UspComparison.tsx:91`, `src/sections/UspComparison.tsx:174-176`
**Issue:** The Price-per-drink row encodes the asterisk as a literal
character suffix inside the capshot column string (`'₹24-₹30 per cap*'`)
and the explanatory footnote renders as an unrelated `<p>` sibling after
the `<table>`:

```tsx
// line 91:
capshot: '₹24-₹30 per cap*',

// lines 174-176:
<p className="mt-3 text-xs text-[color:var(--color-fg-muted)]">
  * CAPSHOT per-cap price range pending client final approval before Phase 6.
</p>
```

There is no `aria-describedby`, `aria-details`, `<sup><a href="#..."/></sup>`,
or any other mechanism connecting the two. A screen-reader user navigating
by cell hears "₹24-₹30 per cap asterisk" and has no way to locate the
disclaimer. For a sighted user the association is obvious because the
footnote visually follows the table and starts with "*"; for an
AT user there is nothing — the asterisk is announced as "star" or
"asterisk" with zero context.

The source comment on line 168-173 explicitly acknowledges the choice
("positioned OUTSIDE the semantic `<table>` as a sibling `<p>`... no
screen-reader table-structure disruption") but conflates "doesn't disrupt
table semantics" with "is accessible." The footnote exists specifically
BECAUSE the price range is provisional pending Phase 6 — hiding that
caveat from AT users carries legal/compliance risk under the regulator-safe
posture the comparison section is designed around (D3.1-01, FSSAI prep).

**Fix:**

```tsx
// Give the cell + footnote matching ids and wire them with aria-describedby.
// Change the capshot column render to include a <sup> link OR
// wire aria-describedby on the <td> itself:

// Option A — aria-describedby on the capshot <td>:
<td
  className="py-4 text-sm font-bold text-[color:var(--color-brand-rose)] sm:text-base"
  {...('pricingPending' in row
    ? { 'aria-describedby': 'usp-pricing-footnote' }
    : {})}
>
  {capshot}
</td>

// ...and give the footnote the id:
<p id="usp-pricing-footnote" className="mt-3 text-xs text-[color:var(--color-fg-muted)]">
  * CAPSHOT per-cap price range pending client final approval before Phase 6.
</p>

// Option B — swap the trailing '*' literal for a <sup> that links to the footnote:
// (requires splitting the capshot string into {label}<sup>…</sup>).
```

Option A is less invasive and keeps the data tuple strings pure. Either
way, screen readers announce the footnote after the cell content and the
provisional-price caveat is actually reachable.

### IN-01: `pricingPending: true as const` discriminator is truthy-insensitive via `in` operator

**File:** `src/sections/UspComparison.tsx:92`, `src/sections/UspComparison.tsx:141-144`
**Issue:**

```tsx
// ROWS tuple:
pricingPending: true as const,
// ...
const pricingProps =
  'pricingPending' in row
    ? { 'data-pricing-pending': 'true' as const }
    : {};
```

`'pricingPending' in row` tests **key presence**, not truthy value. If a
future row adds `pricingPending: false` (or any falsy value), the row
would still receive `data-pricing-pending="true"` on its `<tr>`. The
`as const` on `true` makes TypeScript's discriminated-union narrowing
precise today, but the runtime check doesn't honor the type's intent.

Impact: zero bug today — only one row has the key and its value is
`true`. Hardening suggestion only.

**Fix:**

```tsx
const pricingProps =
  'pricingPending' in row && row.pricingPending === true
    ? { 'data-pricing-pending': 'true' as const }
    : {};
```

Or key off a non-boolean discriminator (e.g., `pricingNote: '…'` string)
whose presence always implies the pending state.

### IN-04: Step-marker label uses em-dash separator; may not surface in heading-navigation

**File:** `src/sections/CatalogBundles.tsx:103`, `src/sections/CatalogBundles.tsx:126`
**Issue:** The step label text uses an em-dash (U+2014) as the separator:

```
Step 1 — Pick your flavor
Step 2 — Pick your pack
```

Two secondary observations:

1. The step markers are plain `<span>` text nodes — they do NOT appear in
   screen-reader heading navigation. A VoiceOver user scanning by heading
   level sees `h2 "Pick your CAPSHOT." → h2 "Pick your flavor." → h4
   bundle titles` and never perceives "Step 1 / Step 2" scaffolding at
   all. The scaffolding's whole purpose (make the two-step narrative
   explicit) only lands for sighted linear-reading users. If the goal is
   to make the two-step narrative accessible to AT users navigating by
   heading, the scaffolds would need to be `<h3>` siblings or an
   `aria-level="3"` role=heading. Alternatively the step pills could use
   `<p>` with `role="group"` + an `aria-labelledby` tying each sub-section
   back to its step. Current implementation is a sighted-user-only
   affordance.

2. Em-dash separators are read differently across AT engines (VoiceOver
   often reads as a pause; some older TalkBack builds read "dash"). Not a
   bug but a minor consistency note vs. an ASCII hyphen or a bullet.

**Fix (optional):** Consider using the hidden visually-hidden pattern:

```tsx
<span className="sr-only">Step 1: </span>
<span aria-hidden="true" className="...">Step 1 — </span>
<span className="...">Pick your flavor</span>
```

...or elevate the step pill to a lightweight heading if the two-step
narrative is a documented a11y requirement. Pending product decision.
