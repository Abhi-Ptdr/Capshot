## Warnings

### WR-01-R: Heading hierarchy skip inside `<section aria-labelledby="catalog-heading">` — introduced by the Phase 3.1 parent swap

**File:** `src/sections/CatalogBundles.tsx:59`, `src/sections/FlavorTeaser.tsx:125`, `src/sections/Bundles.tsx:79`
**Issue:** `CatalogBundles` emits `<h2 id="catalog-heading">Pick your CAPSHOT.</h2>` as the labelled-by heading of the catalog section. Inside that same `<section>`:

- `FlavorTeaser` (Step 1) renders a second `<h2>Pick your flavor.</h2>`.
- `Bundles` (Step 2) renders `<h3>Pick your pack.</h3>`.

The two children's headings should be siblings at the SAME level under the shared H2. Today one is an H2 (sibling-level to its own parent heading, which is wrong) and the other is an H3 (correct child-level). The resulting outline:

```
h2 "Pick your CAPSHOT."              ← CatalogBundles shared heading
  h2 "Pick your flavor."              ← FlavorTeaser (should be h3)
  h3 "Pick your pack."                ← Bundles (correct)
    h4 "Trial Pack" / "Fitness Pack" / "Bulk Energy Pack"
```

Screen readers interpret this as "end of the H2 heading-level nesting" at FlavorTeaser, so the Bundles tri-card lane is announced as a NEW top-level content block rather than Step 2 of the two-step narrative. Mobile VoiceOver / TalkBack users who navigate by heading-level will not perceive the "pick a flavor THEN pick a pack" sequence the H2 promises.

Why this is a Phase 3.1 finding and not a pre-existing Phase 2 one: before Phase 3.1, `FlavorTeaser` was a standalone section with its own `<h2>` at the top-level outline — correct. The Phase 3.1 parent swap (D3.1-05a) placed it INSIDE a section whose aria-labelledby H2 is one level up, which is the moment the hierarchy breaks. The fix pass could not touch `FlavorTeaser` because of the byte-identical lock, which is understandable — but the lock is a soft constraint, and the a11y defect is real.

**Fix (any of three):**
1. (preferred) Relax D3.1-05a by exactly one line in `FlavorTeaser.tsx:125` — change `<h2>` to `<h3>` — and update the Phase 2 `flavor-teaser.spec.ts` heading-level assertion if it exists. This is a one-line, zero-visual-change edit that corrects the outline.
2. Remove the shared `<h2 id="catalog-heading">` in `CatalogBundles.tsx` and instead use `<p class="eyebrow">` for "Flavor + pack" + no H2 at all, letting FlavorTeaser's existing H2 and Bundles' H3 both be top-level under HomePage's `<main>`. This keeps FlavorTeaser byte-identical but drops the "two-step shared narrative" that CatalogBundles was designed to express — a product-level trade-off that needs the client's sign-off.
3. Downgrade `Bundles`' `<h3>` to a sibling H2 of FlavorTeaser's H2 so at least both children match. This "fixes" the inconsistency but leaves the H2-under-H2 anti-pattern in place. Not recommended.

Lighthouse Accessibility and axe-core will flag this (`heading-order` rule).

### IN-02-R: `Bundles.tsx` uses `React.CSSProperties` without importing `React` — relies on UMD global declaration

**File:** `src/sections/Bundles.tsx:47-50`
**Issue:** `Bundles.tsx` imports no `React` symbol but references `React.CSSProperties` twice. This compiles today only because `@types/react` ships a UMD global `namespace React` declaration, which TypeScript resolves against. With `jsx: "react-jsx"` (verified in `tsconfig.json:7`), source files do NOT need `import React` for JSX, but they DO need an explicit import for `React.*` type references under the modern convention.

Impact: works today; brittle under future `@types/react` changes (e.g., if the UMD global is dropped) or stricter linting (`@typescript-eslint/no-restricted-globals`). The file is inconsistent with the rest of the Phase 3.1 code which uses explicit `type { ... } from 'react'` imports (`TrustBadge.tsx:2`, `types.ts`, etc.).

**Fix:**
```ts
import type { CSSProperties } from 'react';
// ...
const cardStyle: CSSProperties = {
  ['--cap-base' as string]: BRAND_ROSE,
  ['--cap-highlight' as string]: lightenHex(BRAND_ROSE, 15),
};
```
Also drops the trailing `as React.CSSProperties` cast on line 50 which is now redundant.

### IN-03-R: `getCta` still uses `.slice('bundles.'.length) as 'trial' | 'fitness' | 'bulk'` — a type assertion that TypeScript cannot prove

**File:** `src/config/cta.ts:124`
**Issue:** The CR-01 fix successfully removed the dangerous `slot as 'primary' | 'secondary' | 'nav'` assertion, but a smaller assertion survived inside the `bundles.*` case:

```ts
const key = slot.slice('bundles.'.length) as 'trial' | 'fitness' | 'bulk';
```

Within the three case labels, TypeScript narrows `slot` to `'bundles.trial' | 'bundles.fitness' | 'bundles.bulk'`. The compiler knows `.slice(8)` returns a `string`, not any narrower type — hence the `as`. The runtime value is always one of the three target literals because the three cases exhaustively enumerate them, so the assertion is safe TODAY. But if a future `CtaSlot` literal like `'bundles.subscription'` is added and its case label is folded into the same case cluster by a careless edit, the assertion silently widens to a wrong literal.

**Fix:** Replace with an explicit per-case return (verbose but no assertion needed):

```ts
case 'bundles.trial':
  return buildBundleCta('trial');
case 'bundles.fitness':
  return buildBundleCta('fitness');
case 'bundles.bulk':
  return buildBundleCta('bulk');
```

with `buildBundleCta` extracted as a local helper. Or use a lookup table keyed by the full `CtaSlot` literal.

Severity: Info because the assertion is well-scoped and the exhaustive `default` throw catches any runtime drift; this is a hardening suggestion, not a bug.

### IN-04-R: `TrustBadge` dev-warning banner uses `role="status"` for a static mount-time warning — needless live-region announcement

**File:** `src/components/ui/TrustBadge.tsx:110`
**Issue:** The `data-pending-fssai` dev-only warning banner declares `role="status"`. `role="status"` is an ARIA live region that screen readers announce when the element's content changes (polite announcement). For a banner that renders statically on mount with fixed text, this creates a one-shot polite announcement that is already covered by the element being in the normal reading order. The live-region role is unnecessary.

Impact: dev-only (production throws before reaching this branch per TRUST-02 contract), so zero user-facing impact. Semantic nit for consistency with the rest of the component.

**Fix:** Remove `role="status"` on line 110, or replace with `role="alert"` only if the authors genuinely want VoiceOver / NVDA to interrupt the current speech on first render — which is probably over-aggressive for a dev warning.
